# Traffic Cat 首页 AtriGal 化重构设计稿

## 1. 目标

本轮设计只解决一个问题：

把当前“说明很多、入口很多、每一块都在解释自己”的首页，
收敛成一个更像 `GalGame` 场景首页的值守界面。

改造后的第一感受应当是：

- 第一眼先看到角色正在汇报情况
- 紧接着就能扫到关键数据和下一步动作
- 文案明显更有角色感，但不影响看状态
- 首页不再像产品介绍页，而像“角色 + 情报台”

本轮目标不是新增功能，而是重做首页的表达层级、文案口吻和信息密度。

## 2. 范围与非目标

### 2.1 本轮范围

- 重构 `RealtimePage` 的首页信息结构
- 调整侧边栏与首页的文案口吻
- 压缩首屏解释性文案
- 重新定义首页区块优先级
- 让首页口吻贴近用户指定的 `Atri` 式天然可爱风格

### 2.2 本轮不做

- 不改 Rust / Tauri / IPC 协议
- 不改数据采集逻辑
- 不改历史检索、进程详情等页面的功能边界
- 不扩剧情系统、角色养成、多角色切换
- 不做全站视觉风格彻底翻新

## 3. 当前问题

现有首页已经具备较好的视觉基础和挂件气质，但体验上存在明显负担：

- 首屏同时存在侧边说明、Hero 说明、分区摘要、状态 banner、卡片解释
- 多个区域在重复表达同一件事，例如当前状态、当前能力、下一步动作
- 首页大量使用“把……看清”“先确认……再决定……”这类说明书句式
- 挂件编辑、诊断准备、重点信号都在首屏争抢注意力
- 角色存在感有了，但她说话的方式还不像一个明确的人格

结果是：

- 用户第一眼需要“读很多字”才能理解首页
- `GalGame` 气质被解释性文案冲淡
- 信息虽然全，但缺乏真正的主次

## 4. 产品设计结论

### 4.1 首页定位

首页应当是：

“一个有点天然、会认真报情况的小搭档，正在把桌面联网动静递到你面前。”

它不是完整教学页，也不是纯数据看板。

它更像：

- 上方有一个场景舞台
- 角色说一句话
- 旁边摆一小块情报台
- 下方再给两个真正必要的次级区块

### 4.2 核心体验闭环

用户进入首页后应当形成下面这条路径：

1. 先看到角色正在报一句话
2. 紧接着扫到当前关键状态与流量结论
3. 明白“现在是谁最值得看”
4. 明白“下一步应该追哪一条”
5. 如果想深挖，再往下看热点流量和诊断准备度

## 5. 文案人格与口吻

### 5.1 人格目标

首页口吻统一贴近用户指定的 `Atri` 风格：

- 天然一点
- 可爱一点
- 认真汇报
- 主动观察
- 不油腻
- 不恋爱陪聊

不采用以下方向：

- 不走傲娇侦探风
- 不走大小姐命令风
- 不走宅梗堆砌风
- 不走手游公告风

### 5.2 文案分层

首页文案只允许分成三层：

1. 角色台词
2. 状态旁白
3. 系统标签 / 动作提示

其中：

- 角色台词最有角色感
- 状态旁白短而轻
- 数据标签和操作词保持清楚直接

### 5.3 角色台词风格

首页主舞台的角色台词应贴近下面这种风格：

- `咦，它又偷偷连出去了呢。`
- `发现新动静了，我已经记下来了。`
- `这个目标还没有交代清楚呢。`
- `有一点可疑，不过别担心，我会继续看着。`
- `刚刚那条链路，我已经注意到了。`

要求：

- 每次只出现一句
- 优先控制在 `22` 个字以内
- 语气像主动汇报，不像卖萌表演

### 5.4 状态旁白风格

状态旁白比台词更短，像角色顺手补的一句说明：

- `先用回退链路看着`
- `真实链路已经接上了`
- `现在还算安静`
- `有新的外连冒出来了`
- `这条链路还没看完整`

### 5.5 导航与区块副标题风格

导航副标题和区块摘要不再写成功能介绍，而是写成轻旁白：

- `实时流向` -> `刚刚的动静，我都替你盯着`
- `进程聚合` -> `这些目标最近都不太安分`
- `进程详情` -> `单独看看它到底在忙什么`
- `历史检索` -> `之前发生过的事，也能翻出来`
- `诊断` -> `让我看看还有哪里没接好`

## 6. 首页信息结构

### 6.1 结构总览

首页重构后采用：

- 一个主舞台区
- 两个次级区块
- 若干被降权的辅助能力

即：

1. 主舞台区
2. 热点流量区
3. 观测准备度区
4. 挂件编辑能力下沉为辅助块

### 6.2 主舞台区

主舞台区是首屏主角，采用“角色 + 情报台”的双主角布局。

左侧内容：

- 角色主视觉或挂件主场景
- 一句角色台词
- 一句短状态旁白

右侧内容：

- `上行`
- `下行`
- `状态`
- `当前榜首`
- `下一步`

主舞台只回答 4 个问题：

- 现在是谁最活跃
- 当前上下行大概多大
- 当前属于什么状态
- 下一步该看哪

### 6.3 热点流量区

热点流量区继续保留，但表达更直接。

这里优先承载：

- 谁在连
- 连到哪
- 当前速率
- 最近活动时间

区块标题与空态文案可带轻微角色味，
但列表本身保持工具化呈现。

### 6.4 观测准备度区

观测准备度区保留诊断价值，但从“教学区”改成“状态区”。

默认只展示：

- 当前平台
- 当前观测能力
- 一条推荐动作
- 一个可展开的检查入口

`SetupChecklist` 仍保留，但不默认以大段说明形式占首屏。

### 6.5 挂件编辑区

挂件编辑能力不删除，但降权处理。

首页只保留：

- 一个简短标题
- 一句短提示
- 直接可操作的控件

删除围绕控件的大段解释语。

## 7. 首屏内容删减策略

### 7.1 首屏直接移除或压缩的内容

以下内容不再以当前形式出现在首屏核心区域：

- 长 `lead`
- `battleReport` 这类补充说明
- 4 张都带解释段落的 KPI 卡
- “挂件解释 / 首装护航 / 当前重点” 三块同时平铺
- 多层 banner 对同一状态的重复解释

### 7.2 首屏保留的必要信息

首屏仅保留以下最必要内容：

- 页面标题
- 一句角色台词
- 一句状态旁白
- 3 个核心数值
- 1 条当前热点
- 1 条下一步动作
- 1 条简短状态标签

### 7.3 下沉原则

凡是满足下列任一条件的内容，都应从首屏降权：

- 需要连续读两句以上才能懂
- 与主舞台表达的是同一件事
- 不是用户进入页面 2 秒内必须知道的信息
- 已经有诊断页或次级区块承接

## 8. 组件与文件改造

### 8.1 主要改造文件

本轮主要涉及：

- `apps/desktop-ui/src/pages/RealtimePage.tsx`
- `apps/desktop-ui/src/copy/galAbstract.ts`
- `apps/desktop-ui/src/app/App.tsx`
- `apps/desktop-ui/src/styles.css`
- `apps/desktop-ui/src/themes/botanical-theme.css`

### 8.2 `RealtimePage.tsx`

改造重点：

- 重组首页区块顺序
- 删除或压缩大段 lead / summary / explanation
- 用主舞台替代现有“hero + 多解释卡”的组合
- 将诊断摘要与检查入口收敛成一块
- 将挂件编辑区降为辅助区域

### 8.3 `galAbstract.ts`

改造重点：

- 重写首页相关文案
- 为主舞台增加角色台词与短状态句
- 压缩导航副标题
- 压缩区块标题和摘要
- 重新组织 mock / fallback / live 状态说法

### 8.4 侧边栏

改造重点：

- 副标题缩短
- 导航副标题更轻、更像角色旁白
- 概览卡减字，必要时减量

目标是让侧边栏更像角色目录和页签，而不是一列说明卡。

## 9. 视觉与交互原则

### 9.1 主舞台优先

视觉上必须确保主舞台成为首页唯一强主角。

不允许出现：

- 多个大区块同权竞争
- 同一层级出现太多摘要段落
- 每张卡都像要讲完整故事

### 9.2 角色与数据并重

本轮采用“台词化双主角”方向：

- 角色负责开口
- 数据负责定案

两者权重接近，但角色不能压过数据，
数据也不能把角色挤成纯装饰。

### 9.3 文字长度规则

首页文案控制规则如下：

- 标题：`2` 到 `6` 个字
- 角色台词：优先不超过 `22` 个字
- 状态旁白：优先不超过 `16` 个字
- 卡片解释：尽量不写，必须写时不超过 `14` 个字
- 下一步动作：只写动作，不写长解释

## 10. 风险与约束

本轮必须防止以下问题：

### 10.1 角色感压过工具性

角色台词只能出现在关键位置，
不能让用户为了看状态去读一段表演文本。

### 10.2 哪里都在说话

首页只能有一个最会说话的区域，即主舞台。
其余区域必须克制。

### 10.3 人格跑偏

文案不能滑向：

- 恋爱陪聊
- 过度撒娇
- 大小姐命令口吻
- 重宅梗与中二腔

### 10.4 重构伤到业务逻辑

本轮只允许重构页面结构、文案和视觉优先级，
不改现有数据接口与业务能力边界。

## 11. 验收标准

改造完成后，应满足以下判断标准：

- 用户进入首页 2 秒内能看懂当前谁最活跃、当前状态、下一步看哪
- 首页不再需要连续阅读多段解释才能理解
- 首页整体读起来像同一个角色在认真报情况
- 文案明显更像 `GalGame` / `Atri` 式气质，但不妨碍扫数据
- `mock / fallback / live` 仍能被快速区分
- 侧边栏与首页不再同时堆积大量解释性副标题

## 12. 实施建议

本轮实现建议按以下顺序推进：

1. 先重写首页与侧边栏文案
2. 再重组 `RealtimePage` 结构
3. 再收缩诊断摘要与挂件编辑区
4. 最后做样式层级调整与响应式验证

这样可以先确保语气和结构正确，再进入视觉精修。
