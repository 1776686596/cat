# Traffic Cat 挂件场景层 v0.1 设计稿

## 1. 目标

本轮设计只解决一个问题：

把当前“会动的联网挂件”收敛成“有角色反应、能被解释、适合录屏传播的小家伙”。

对应用户感受应当是：

- 第一次打开就觉得这东西有点意思
- 看见角色变化时能大概猜到发生了什么
- 点开主界面后能立刻看懂她为什么刚才那样

本轮设计的主目标不是补全监控功能，而是先打通“有趣 -> 看懂 -> 愿意留下来”的最小闭环。

## 2. 范围与非目标

### 2.1 本轮范围

- 为挂件定义稳定的 5 态角色场景模型
- 新增统一的前端 `scene` 视图层
- 让挂件和实时页共用同一套场景解释
- 为无权限或演示场景提供稳定轮播的 demo 模式

### 2.2 本轮不做

- 不改 Rust 后端协议
- 不新增页面
- 不扩复杂历史检索、筛选和图表
- 不做剧情系统、养成系统和多角色系统
- 不追求采集精度细节优化

## 3. 当前实现问题

现有前端已经具备较好的视觉基础：

- 挂件组件已有表情、气泡、排行和拖拽能力
- 实时页已有挂件预览区、重点信号区和热点连接区
- 文案层已经具备“守望挂件”口吻

但产品闭环仍然缺一层统一抽象，导致以下问题：

- 角色反应逻辑散落在挂件组件内部
- 挂件状态、表情、台词、提示文案并非同一来源
- 主界面能看数据，但没有明确解释“她为什么刚才这样”
- 演示模式更像静态 mock，不适合录 GIF 和首次试玩

## 4. 产品设计结论

### 4.1 产品定位

`Traffic Cat` 在 v0.1 的对外感知应当是：

“一个会替你盯着电脑联网、还会自己有反应的小家伙。”

因此挂件应当优先承担以下职责：

- 用表情和短台词把网络变化翻译成人能直觉理解的反馈
- 用最少信息告诉用户当前是否值得注意
- 把主界面变成“解释层”，而不是让主界面抢走第一印象

### 4.2 最小体验闭环

用户体验应当形成下面这条路径：

1. 看到桌面角落的角色挂件
2. 角色因联网变化做出明显反应
3. 用户通过一句台词和速率知道大概发生了什么
4. 点击进入主界面，马上能看到“她刚才为什么这样”

## 5. 场景模型

### 5.1 固定 5 态

本轮统一使用以下 5 个前端场景态：

- `idle`
- `watching`
- `busy_download`
- `busy_upload`
- `alert`

其中 `watching` 为前端派生态，不要求后端直接提供。

### 5.2 判定优先级

判定顺序固定为：

`alert > busy_upload > busy_download > watching > idle`

### 5.3 场景含义

#### `idle`

- 无明显活跃连接
- 角色安静值守，不打扰用户

#### `watching`

- 存在活跃连接，但速率不高
- 角色表现为留意、观察、不急着下结论

#### `busy_download`

- 当前以下行为主，且速率已越过活跃阈值
- 角色表现为兴奋、热闹、注意力被吸走

#### `busy_upload`

- 当前以上行为主，且速率已越过活跃阈值
- 角色表现为认真、盯紧、开始警觉

#### `alert`

- 命中提醒态，或运行链路异常
- 角色明确提醒用户“建议看一眼”

### 5.4 判定规则

前端以当前快照派生场景：

- 有运行错误，或原始 `widgetState` 为 `alerting` 时进入 `alert`
- 没有活跃连接时进入 `idle`
- 总上行显著高于总下行且超过活跃阈值时进入 `busy_upload`
- 总下行显著高于总上行且超过活跃阈值时进入 `busy_download`
- 其他存在活跃连接的情况进入 `watching`

## 6. 统一 scene 视图层

### 6.1 新增文件

新增前端视图构造层：

- `apps/desktop-ui/src/data/widgetScene.ts`

### 6.2 职责

该文件负责将：

- `RealtimeSnapshotView`
- `DashboardRuntimeView`

转换为统一的 `WidgetSceneView`，供挂件和实时页共同消费。

### 6.3 输出内容

统一输出至少包含：

- `sceneId`
- `mood`
- `stateLabel`
- `title`
- `line`
- `overlayLead`
- `guidance`
- `reasonTitle`
- `reasonDetail`
- `focusProcessName`
- `focusTarget`
- `focusRateLabel`

这意味着后续组件不再自己理解网络状态，只渲染“角色当前这一幕”。

## 7. 组件与页面改造

### 7.1 挂件组件

修改：

- `apps/desktop-ui/src/components/widget/TrafficWidgetCard.tsx`

改造原则：

- 组件保留展示、拖拽、榜单和动画
- 状态标题、默认台词、引导文案、角色表情统一从 `scene` 读取
- 组件内部不再直接判断“现在是下载态还是提醒态”

气泡逻辑继续保留，但改为由下列变化触发：

- `sceneId` 改变
- 焦点连接改变
- 运行错误出现

### 7.2 实时页

修改：

- `apps/desktop-ui/src/pages/RealtimePage.tsx`

新增一张“挂件解释”卡片，明确展示：

- 她现在是什么状态
- 当前反应由什么连接触发
- 用户接下来先看哪里

实时页要承担“解释她刚才为什么这样”的职责，而不是只做数据看板。

## 8. 文案层改造

修改：

- `apps/desktop-ui/src/copy/galAbstract.ts`

新增集中化文案配置，按场景组织：

- `stateLabel`
- `reasonTitle`
- `lines`

要求：

- 每句台词尽量控制在 8 到 18 个字
- 用词保持“轻提醒、轻陪伴、不过度演”
- 避免系统日志感和过度角色扮演感

## 9. 演示模式设计

### 9.1 改造位置

修改：

- `apps/desktop-ui/src/bridge/mockDesktopBridge.ts`

### 9.2 设计原则

演示模式不应只返回固定一套数据，而应按时间片轮播 5 个场景：

1. `idle`
2. `watching`
3. `busy_download`
4. `busy_upload`
5. `alert`

### 9.3 目的

这样可以同时满足：

- 没有真实权限时也能完整演示
- README GIF 可稳定录制
- 首次试玩时能快速理解产品卖点
- 挂件和主界面始终处于同一场景，不会割裂

## 10. 验收标准

本轮设计完成后，应满足以下判断标准：

- 第一次打开，用户 10 秒内能理解挂件是“会盯联网的桌宠”
- 30 秒内能看到至少 3 种不同角色反应
- 不打开主界面，也能觉得挂件本身有意思
- 点击主界面后，能立刻看懂她当前反应的原因
- 无真实权限时，仍能通过 demo 模式展示完整产品气质

## 11. 实施范围拆分

本轮实现分为 5 个文件层面的动作：

1. 新增 `widgetScene.ts` 统一 scene 视图层
2. 改造 `TrafficWidgetCard.tsx` 为纯展示组件
3. 改造 `galAbstract.ts` 集中文案
4. 改造 `RealtimePage.tsx` 增加解释卡片
5. 改造 `mockDesktopBridge.ts` 增加 5 幕轮播 demo

以上 5 项能独立形成一个可演示、可理解、可继续扩展的 `v0.1` 闭环。
